# Requirements Document

## Intake

**Problem:** The rules that decide whether a spec may advance — who approved it, whether the approved text changed afterwards, whether a ticked task was ever run, whether two sessions are writing the same file — exist only as prose in skills and as three hand-kept copies of two scripts, so none of them is enforced anywhere a machine can see. Today a spec's stage is inferred from which files exist. No approval is recorded anywhere, so "approved" cannot be checked in CI. A task can be ticked `[x]` by any writer, including Kiro's own "Run all tasks", with nothing linking the tick to a command that ran. And the spec checks CI runs are a different copy of the code from the one the assistant skills run. Each incident this repository has recorded is the same failure: a rule that lived in prose rather than in a check. They include a skill pointing at a file that did not exist, `${CLAUDE_PLUGIN_ROOT}` collapsing to `/scripts/…`, copies drifting apart, one session sweeping another's edits into a commit, and a stale `[-]` surviving an interrupted run.

**Risk class:** critical. The change touches three of the class's triggers, each on its own sufficient. It decides **permissions**: who may approve an artifact, and that an assistant never may. It handles **credentials**: CI obtains the Platform from a possibly private source, and evidence and ledger records sit next to command lines that can carry a token. And it defines an **externally visible contract**: the Markdown protocol, the task markers Kiro parses, the command surface and exit statuses CI pipelines in other repositories depend on, and a ledger format that becomes permanent once the first approval is written into it. A wrong approval rule either lets an agent approve its own work or blocks every merge. A wrong ledger format corrupts the audit trail it exists to protect.

**Lifecycle path:** full spec, both review gates, and no shortcut for speed. Both gates matter here in a way they rarely do. This spec specifies the gates themselves, so a gap in it is a gap in every spec that later runs through the Platform. Delivery is still incremental. Each requirement carries a **Delivery slice** line, so design and tasks can plan Slice 1 first and prove it on one live spec before anything else is built.

The pre-execution check (old R46, now Requirements 002:18 and 003:15) exists because Kiro re-reads requirements and design before it executes each task, and today's `spec-implement` follows the same sequence: re-read, implement, then verify against the same criteria. ## Introduction

This repository writes every piece of work as a spec first — requirements, design, tasks — and runs it through three assistants. The discipline works while each author follows it. It stops working the moment a rule depends on someone remembering. An approval exists only as a sentence in a chat. A ticked task proves only that something ticked it. The script CI runs is not the script the skill ran. And the lifecycle is whatever files happen to be present. The spec engine that carries the discipline today was never built to hold state. It is prose instructions plus two stateless scripts, copied into each repository that uses them.

The SDLC Platform is a spec-driven development engine **built from scratch**. It uses the sdlc plugin 0.2.0 as a behavioural reference for what must still be possible, not as code to extend. Its premise is the plan's closing sentence: the engine owns the truth, and Markdown, Kiro, Claude Code, OpenCode and CI are interfaces to it. The engine keeps that truth in git and nowhere else:

- Lifecycle state and artifact versions sit in each document's frontmatter.
- Approvals, decisions, evidence, claims and amendments sit in an append-only, hash-chained ledger beside the documents they concern.

A reviewer reading a merge request therefore sees a state change as a diff. CI can recompute each claim from the commit alone.

Two decisions shape everything downstream.

- **An approval is a human act that CI can check.** Two kinds of approval count: a merge-request approval by an identity the repository's own approval policy authorises, or a commit signed by such an identity. No assistant can approve anything, its own work included. A git author name is not an identity. An approval is bound to one exact version of the artifact, so any later change to the approved text voids the approval.
- **Evidence is written by the engine, never by the agent.** The engine runs the command itself. It records what ran, the exit status and when, against which commit and which paths, but never the output. So a completed task means a command the engine watched exit zero. It no longer means an agent reported one.

Kiro's own task runner can still tick a box. The Platform does not forbid that. It reports the tick as a distinct state, unverified completion, which strict verification rejects.

The work ships in four slices, and Slice 1 must prove the design end to end on one live spec before the rest is built. Since 2026-09-25 each slice is its own Child Spec with its own approvals (`## Programme`). This document keeps what is common to all four: the problem, the discovery, the Glossary, the out-of-scope decisions and the assumptions.

**Users:**

- **Spec Author**: the agent running the requirements, design or tasks stage, or the human editing those documents, who produces an Artifact Version for review.
- **Approver**: a human who is an Authorised Approver under the Approval Policy and who gives an Approval Signal for one Artifact Version.
- **Executing Agent**: the Assistant Session that runs one task and asks the Evidence Recorder to record the task's Verification Command.
- **Orchestrating Agent**: the Assistant Session that runs execution control across tasks and waves.
- **Kiro Operator**: a human who opens a spec in Kiro and may start tasks through Kiro's own task controls.
- **CI Pipeline**: the Consumer Repository's pipeline, on GitLab for basalt, which runs the Platform's checks on each merge request without an Assistant or a stored secret.
- **Consumer Maintainer**: the person who installs, pins, upgrades and configures the Platform in a Consumer Repository.
- **Platform Maintainer**: the person who releases a new version of the Platform.
- **Reviewer**: the review-gate agents and the humans reading a merge request, who need each state change to be visible as a diff.

**Business outcome:** once this ships, an artifact counts as approved only when CI can verify a human approved it, and work counts as done only when CI can verify the engine watched it pass. Both are recomputed from git on each merge request by one implementation, the same one that every assistant, every skill and CI invoke.

**In scope:** The requirements are delivered in four slices, each held by one Child Spec. `## Programme` gives the counts, and `## Requirement map` maps each old requirement.

**Out of scope:**

- **A web UI.** The plan names one only as a future consumer of the Decision Contract. Requirement 003:6 keeps the contract renderer-neutral so a UI can be added without changing it.
- **Hosting a server or a database.** Git is the database (Requirement 002:4). A service would be a second source of truth, which the plan and ADR-0054 both reject.
- **Deciding a product's tenancy, domain or role model.** basalt is domain- and tenancy-agnostic (ADR-0043, ADR-0049). The Approval Policy names identities, not roles a product defines.
- **Bidirectional synchronisation with Kiro's own spec UI.** The Platform reads Kiro's markers and detects evidence-less completion, and nothing more. A deliberate two-way contract would be a later spec, which the plan's §36 anticipates.
- **Replacing basalt's non-spec tooling.** `validate`, `scaffold`, `ci:*`, `imports:check` and `decorators:proof` govern the workspace, not the spec lifecycle.
- **Extending the sdlc 0.2.0 code.** That code is the behavioural reference. Its prose contracts carry over where they do not conflict (Assumption 2). Its scripts do not.
- **Writing or superseding ADRs, and correcting the six stale claims under Constraints.** That is `architecture-guardian` and `docs-governance` work. This spec records the need.
- **Choosing the package name and distribution channel.** Design decides this (Assumption 3). The requirement is what the channel must guarantee (Requirement 002:1).
- **Migrating the content of basalt's other 22 specs.** Requirement 002:14 adopts one spec, and Requirement 003:9 supplies the migration a human then runs per spec.
- **A shunt-style inference gateway inside the Platform** (Amendment 1). It is a developer-environment choice, and it needs a data-governance decision. Requirement 003:14 governs what the Platform sends to such a gateway, not the gateway itself.
- **Code semantic indexing** (Amendment 1). It belongs to the Assistants, or to an external MCP server. Requirement 002:16 also rules out a Persistent Store, which an index would be.
- **Using an advisory model for any Gate** (Amendment 1). A Suggestion is never a Gate input, an approval or evidence (criteria 004:13.9 to 004:13.12).
- **A persistent database or index of any kind, local ones included** (Amendment 1). Platform State is repository content only, and any cache is a Disposable Cache (criteria 002:16.7 to 002:16.12). This extends the "server or database" item above to the host.
- **Governing an Assistant's own model traffic** (Amendment 1). The Platform is not in an Assistant's request path. The Egress Guard governs content the Platform itself sends (Requirement 003:14). The OpenCode provider allow-list (criterion 004:14.4) is the one place the Platform configures an Assistant's own providers, and it does so through that Assistant's policy mechanism (Assumption 37).
- **A per-spec reference file, and a separate per-package manifest file** (Amendment 1). A second copy of facts the manifests already hold drifts. Requirement 003:16 derives those facts, and keeps the declared rest in one block of the existing manifest.

## Quality Rules Applied To This Document

Every criterion in the four Child Specs was checked against the INCOSE rules. The stated exceptions below name criteria in child numbering; each child's own Quality Rules section adds the exceptions for its 2026-09-25 requirements.

| Rule                        | Meaning                                                                         |
| --------------------------- | ------------------------------------------------------------------------------- |
| Active voice                | The system is the subject and it acts. Not "the record is updated".             |
| No vague terms              | No "quickly", "adequate", "reasonable", "user-friendly", "robust", "efficient". |
| No pronouns                 | Repeat the noun. "it", "they", "this" are ambiguous under review.               |
| Consistent terminology      | One name per concept, matching the Glossary, every time.                        |
| Explicit conditions         | Triggers and states are stated, never implied.                                  |
| Measurable criteria         | A tester can determine pass or fail without asking a question.                  |
| One thought per requirement | No compound behaviour behind a single number.                                   |
| No escape clauses           | No "where possible", "if feasible", "as appropriate", "if practical".           |
| No absolutes                | No "never", "always", "all", "100%", "every conceivable".                       |
| Solution-free               | What the system does, not the class, table, queue or library that does it.      |
| Prefer positive statements  | Say what the system does rather than `SHALL NOT`.                               |

Four rules carry a stated exception, so a reviewer does not read the exception as a miss.

**Solution-free.** Several criteria name an externally fixed contract, because in each case the name _is_ the requirement:

- the `requirements.md`, `design.md` and `tasks.md` document names;
- the four Task Markers and the Kiro Task Line Grammar (Requirements 002:10 and 003:2), which Kiro parses;
- the Question Tool Limits (003:6.5);
- the EARS pattern keywords (004:1.1–004:1.3);
- OIDC (002:1.5), and GitLab and GitHub (002:1.9, 004:9.5), the Hosting Platforms the Consumer Repository and the Platform repository run on;
- Semantic Versioning 2.0.0 (004:10.1);
- the two Risk Class declaration forms (003:9.9), which are the existing specs' literal text.

Requirement 002:4's "hash-chained" and "digest" name a property, tamper-evidence, that the brief fixes as a requirement. The digest algorithm is left to design.

**No absolutes.** The Glossary entry for Prompt Catalog says "every Prompt", and Requirement 004:9's user story says "every consumer". Both are in definitions or stories, not criteria. Several criteria say "each", which is bounded by the named set.

**One thought per requirement.** Criteria 002:6.1, 002:7.12, 002:9.2, 003:7.1, 003:7.3, 004:6.1, 004:7.1 and 005:1.1 list the fields of one record or the checks of one gate.
